# Обновление существующего проекта

Миграция рассчитана на структуру приложенного проекта. Реальная удалённая БД не была предоставлена для проверки. Вначале выполните весь порядок на staging-копии. Не смешивайте старые и новые backend/frontend во время обновления.

1. **Backup.** Остановите запись в старое приложение. Сделайте проверяемую резервную копию Supabase PostgreSQL (включая Auth и прикладные таблицы), старой PostgreSQL с `local_certificate_records`, а также файлов Storage. Резервная копия таблиц Storage не содержит самих файлов! Проверьте восстановление в отдельный проект. Сохраните предыдущий архив приложения и его окружение отдельно от публикуемых файлов.
2. **Apply SQL.** В Supabase → SQL Editor вставьте ВЕСЬ `supabase/migrate_existing_database.sql` → Run. Файл содержит BEGIN/COMMIT, lock_timeout 15 секунд и statement_timeout 120 секунд. Ошибка приводит к отмене транзакции. При большой БД планируйте окно обслуживания и подбирайте время по staging-замеру. Не применяйте частями и не отключайте ограничения ради успешного Run.
3. **Разбор конфликтов.** Существующие дубли email без учёта регистра приведут к отмене создания UNIQUE; сначала разберите их вручную. Существующие дубли незавершённых попыток сохраняются, лишние помечаются timed_out/failed, самая новая остаётся активной. Старые завершённые результаты не удаляются. NOT VALID ограничения сохраняют старые несовместимые строки, но уже проверяют новые записи; список показан вторым результатом verify_database. После проверки старых строк выполняйте VALIDATE CONSTRAINT индивидуально, без массового удаления данных.
4. **Verify.** Выполните `supabase/verify_database.sql`; в первом результате не должно быть FAIL. Проверьте список внешних RPC/policies/Storage buckets в Dashboard: миграция заменяет политики прикладных таблиц из этого проекта, но не может угадать назначение других вручную установленных функций и таблиц.
5. **Legacy.** Если сертификаты выдавались старым backend, заполните только для утилиты `LEGACY_DATABASE_URL` (старое подключение), SUPABASE_URL и SUPABASE_SERVICE_ROLE_KEY (целевой Supabase). Выполните:

```text
node scripts/import-legacy-certificates.mjs
node scripts/import-legacy-certificates.mjs --apply
```

Первый запуск только читает. Второй копирует, не удаляя исходные строки. Все старые номера сохраняются в `legacy_certificates`; первая по времени запись каждой группы user/course становится канонической в `certificates`. UUID пользователя должен соответствовать profiles.id, старый course_id сопоставляется сначала по UUID, затем по slug. Несопоставленные записи сохраняются для публичной проверки, но требуют ручного сопоставления до включения выдачи. Утилита завершается ненулевым кодом при таких записях. Конфликт с уже выданным новым номером останавливает перенос. Частично скопированные строки сохраняются; повторный запуск идемпотентен. Он не является одной распределённой транзакцией между двумя БД, поэтому выполняется при остановленной выдаче. Signed JSON сохраняется приватно; старые /json-потребители должны перейти на новый безопасный ответ.

6. **Окружение.** Скопируйте новый `.env.example`, заполните ключи и PUBLIC_APP_URL/CERT_BASE_URL. При сохранении прежнего домена старые ссылки продолжат работать. Старые скачанные QR невозможно изменить: сохраняйте старый hostname и маршрут либо настройте редирект. После импорта удалите LEGACY_DATABASE_URL из постоянного backend окружения.
7. **Менеджеры.** Новая версия использует `/api/admin/managers`. Удалите старую опубликованную Edge Function `create-manager` через Dashboard → Edge Functions или `supabase functions delete create-manager --project-ref YOUR_PROJECT`. Это удаляет функцию, не пользователей. Оставшийся в архиве index.ts отвечает 410 и служит обозначением устаревшего endpoint. Уже существующие profiles/роли сохраняются.
8. **Установка и проверки.** `npm ci` → `npm run verify:release` → реальные concurrency/REST проверки из TESTING.md.
9. **Запуск.** `npm run dev` для разработки либо `npm start` под supervisor и статический `dist/` за HTTPS reverse proxy в production. Проверьте `/health`, `/readiness`, вход, загрузку файла и сценарий прохождения курса двумя аккаунтами. Убедитесь, что восстановление пароля работает через ваш SMTP.
10. **Deploy.** Разверните frontend/backend вместе. Запустите smoke-тесты на новом origin, проверьте существующий и новый сертификаты, затем откройте доступ участникам. Наблюдайте ошибки/время ответа/квоты Supabase.

## Откат

До COMMIT ошибка уже отменяет транзакцию. После успешного обновления автоматический DROP новых таблиц опасен: он потеряет новые сертификаты/историю и восстановит старые права. Поэтому `supabase/rollback.sql` намеренно read-only. Для отката остановите запись, сохраните новые данные, восстановите pre-migration backup в отдельный Supabase, проверьте его и переключите старое приложение. При повторном переключении согласуйте данные, появившиеся после backup. Откат только frontend без согласования backend/SQL не поддерживается.

Миграция не подтверждает, что старые результаты не были ранее подделаны через доступные тогда интерфейсы. Унаследованные сертификаты остаются унаследованными; пересмотрите сомнительные записи и используйте `status='revoked'`, сохраняя историю.
